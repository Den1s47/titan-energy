# Спецификация MVP: ПАК «Титан-Энергия» (EMS)

Версия: 1.1 (реализация завершена) · Платформа разработки: Hermes agent (GLM) · Развёртывание: Windows-ноутбук, только LAN

> **Статус (21.11.2026):** все срезы M0–M6 реализованы, 47/47 тестов зелёных,
> система проверена вживую (см. §16 «Журнал реализации и изменений»).

Основание: «Техническое задание на создание ПАК Титан-Энергия» (двухуровневая система:
SCADA-уровень сбора данных и оперативного контроля; MES-уровень оперативного управления
энергоэффективностью).

---

## 1. Цели и границы MVP

**Цель MVP** — работоспособный прототип, демонстрирующий все ключевые сценарии ТЗ на
симулированном оборудовании: мониторинг в реальном времени, мнемосхемы с динамической
индикацией, телеуправление, журналы аварий, аналитика ПКЭ/КПЭ, администрирование.

**В MVP входит:**

| # | Блок | Сокращение относительно полного ТЗ |
|---|------|-------------------------------------|
| 1 | Сбор телеметрии ≥ 1 Гц, валидация, архивирование | Протокол сбора — только Modbus TCP (через абстракцию адаптера) |
| 2 | Симулятор оборудования уровня протокола | «Оборудование» = Modbus TCP сервер со сценарным движком |
| 3 | Однолинейная мнемосхема, динамическая индикация | 1 ТП (2 ввода упрощённо → 1 ввод + секция + 4 фидера) вместо предприятия целиком |
| 4 | Телеуправление (двухшаговый алгоритм, блокировки, журнал) | Управление выключателями; РПН трансформатора — заготовка |
| 5 | Журналы (аварии, ненормальные режимы, действия диспетчера, все события), ISA-18.2 | Без звукового сопровождения (заготовка) |
| 6 | Осциллограммы при сработке + просмотр из журнала | Синтезированные симулятором, 1 канал записи на событие |
| 7 | Аналитика: временные ряды, усреднения, гистограммы, КК Шухарта/CUSUM, тепловые карты | Подмножество показателей; PAS-опрос SATEC — вне MVP |
| 8 | Три UI: Admin (users/roles), АРМ диспетчера, MES (общая картина + аналитика) | — |
| 9 | RBAC, аудит действий, работа только в LAN, бэкапы | Без хостing-инфраструктуры, без кластеризации/резервирования узлов |

**Вне MVP (из ТЗ, осознанно отложено):** живые IEC 61850-8-1 MMS, IEC 60870-5-104,
DLMS/COSEM, OPC UA (только интерфейс адаптера и заготовки); СППР (нужны утверждённые
заказчиком регламенты); PAS-прямой опрос SATEC; КПЭ удельных расходов (нужны данные
о продукции); отчёты по согласованным формам; контроль ресурса выключателей по наработке.

## 2. Общая архитектура

### 2.1. Компонентная схема

```
+------------------------ Windows-ноутбук / LAN ----------------------------+
|                                                                            |
|  [simulator]                [collector]                  [web-api]         |
|  Modbus TCP сервер    <--->  asyncio-опрос 1 Гц   <-->    FastAPI           |
|  сценарный движок           валидация/quality            REST + WebSocket  |
|  (нагрузка, аварии,         запись в TSDB                раздача UI        |
|   ТУ-актуаторы)             команды ТУ --> симулятор                       |
|         |                        |                        |                |
|         +----------- TimescaleDB (PostgreSQL 16) ----------+                |
|                                       |                                    |
|                        [SPA: React + Vite]                                 |
|              /admin (Admin UI)  /arm (АРМ)  /mes (MES-уровень)             |
+----------------------------------------------------------------------------+
```

Компоненты:

1. **simulator** — «полевой уровень». Поднимает настоящий Modbus TCP узел; сценарный
   движок пересчитывает регистры 4 раза/с (профиль нагрузки + шум + инъекции аварий +
   имитация задержки актуатора при ТУ). В будущем **удаляется без изменения остальных
   компонентов** — collector переключается на IP реальных устройств.
2. **collector** — опрос ≥ 1 Гц через адаптер, первичная валидация (ТЗ 3.1), присвоение
   quality-флагов, генерация событий (аварии/ненормальные), батчевая запись в TSDB,
   исполнение команд ТУ (write к адаптеру + ожидание смены состояния).
3. **web-api** — REST (объекты, история, агрегаты, журналы, пользователи, ТУ, экспорт)
   + WebSocket (live-снапшоты, поток событий) + статика SPA. RBAC на каждом эндпоинте.
4. **TSDB** — PostgreSQL 16 + TimescaleDB: гипертаблица измерений, continuous aggregates
   для усреднений, сжатие рядов.
5. **SPA** — один Vite-проект, три зоны с ролевым роутингом (§9).

### 2.2. Соответствие уровням ТЗ

| Уровень ТЗ | Компоненты MVP |
|---|---|
| Полевой уровень (счётчики, РЗА, регистраторы ПКЭ, ПЛК) | simulator (заменяемый модуль) |
| SCADA-уровень (сбор, мнемосхемы, ТУ, журналы) | collector + web-api + SPA-зона `/arm` |
| MES-уровень (аналитика, отчёты) | web-api (агрегатные запросы) + SPA-зона `/mes` |
| Двусторонний обмен OT↔IT | write-канал адаптера (ТУ) + REST/WS наверх |

### 2.3. Ключевые архитектурные решения и их обоснование

- **Симуляция на уровне протокола, а не «фейк в коде».** Коллектор ходит настоящим
  Modbus-клиентом в настоящий Modbus-сервер: тестируется реальный путь «опрос → декодирование
  → БД», замена на реальное оборудование = смена конфигурации.
- **Отдельный интерфейс адаптера.** Все протоколы (Modbus сегодня; 104/61850/DLMS/OPC UA
  потом) реализуются одним контрактом (§6.1). Верхние слои не знают протокола.
- **TimescaleDB, а не InfluxDB/Kafka.** Требования ТЗ (усреднения 0,5–15 мин, выборка по
  объекту/параметру/времени, сжатие, SQL-фильтры, тысячи точек/с) закрываются одной
  бесплатной СУБД; брокер сообщений при скоростях MVP избыточен.
- **Embedded-режим для MVP.** simulator+collector могут работать в отдельных процессах, но
  по умолчанию collector встроен в lifespan web-api (один запуск, один лог). Разделение —
  конфигурацией, не кодом.
- **Кастомная разработка вместо готовой SCADA** (Rapid SCADA и т.п.): MES-аналитика ТЗ
  (КК Шухарта, CUSUM, тепловые карты, КПЭ) в готовых бесплатных SCADA не реализуема, а
  итеративная разработка LLM-агентом эффективна на чистом типизированном коде.

## 3. Стек технологий (весь бесплатный)

| Слой | Выбор | Обоснование |
|---|---|---|
| Язык backend | Python 3.12+ | pymodbus/asyncua есть; для LLM-агента — наиболее управляемая генерация |
| Управление окружением | uv | воспроизводимые окружения, не трогает системный python |
| Backend | FastAPI + Uvicorn, pydantic v2 | REST+WS в одном фреймворке, типизированные контракты, автодокументация OpenAPI |
| ORM | SQLAlchemy 2.0 (async) | зрелость, async, лёгкий переход SQLite→Postgres |
| Сбор данных | asyncio + pymodbus (client) | опрос 1 Гц, батчи, таймауты |
| Симулятор | pymodbus (server-режим) | «оборудование» — реальный Modbus TCP узел |
| БД | PostgreSQL 16 + TimescaleDB (Apache-2 edition) | гипертаблицы, continuous aggregates 0,5/1/3/5/10/15 мин, сжатие |
| Realtime | WebSocket (нативный в FastAPI) | снапшоты значений 1 Гц + поток событий |
| Frontend | React 18 + TypeScript + Vite | скорость сборки, строгая типизация для агентной разработки |
| Мнемосхемы | собственные SVG-компоненты React | однолинейные схемы и динамическая индикация ТЗ — готовых бесплатных адекватных нет |
| Графики | Apache ECharts (OSS) | зум, пороговые линии, heatmap, несколько осей Y, большие объёмы точек |
| Состояние UI | TanStack Query + Zustand | серверное состояние + лёгкий клиентский |
| Экспорт | openpyxl (Excel/CSV); опционально LibreOffice headless → PDF | требование ТЗ |
| Auth | JWT (HS256) + роли; пароли PBKDF2 | ТУ с идентификацией оператора — требование ТЗ |
| Тесты | pytest + pytest-asyncio + httpx | контрактные тесты каждого среза |
| Сервисы | Windows Task Scheduler / NSSM | автозапуск, бэкапы по расписанию |

Отвергнутые альтернативы (кратко): Django+Channels (тяжелее для WS-first сценария),
Node.js backend (агент ошибается чаще, слабее научный стек для аналитики),
MongoDB (нет SQL-агрегатов нужного класса), Grafana как основной UI (закрывает графики,
но не мнемосхемы/ТУ; используется опционально как черновая аналитика на этапе M5).

## 5. Модель данных

### 5.1. Справочники и иерархия

- `objects` — древовидная структура (ТЗ: описание вложенности объектов):
  `Предприятие → ТП → Секция шин → Фидер/Выключатель/Трансформатор/Счётчик`.
  Поля: `id, parent_id, type (enterprise|tp|bus|feeder|breaker|transformer|meter), name`.
- `points` — справочник тегов: `id, object_id, code, name, unit,
  kind (analog|discrete), address, scale, phys_min, phys_max, tech_min, tech_max`.
  Включает показатели ТЗ 3.2: S, S1, P, P1, Q1, DQ1, cos φ, PF, U, U1, I, I1, I0,
  THDu, THDi, THDD, К-фактор, дискретные состояния. В MVP-симуляции задействовано
  подмножество: U, I, P, Q, THDu, THDi, PF + дискретные состояния выключателей + код аварии.
- `users`: `id, username, password_hash, salt, role (admin|dispatcher|viewer), is_active`.
- `interlocks` — программные ТУ-блокировки: `id, object_id, condition, message`.

### 5.2. Потоки данных

- `measurements` (гипертаблица): `time, point_id, value, quality (good|suspect|bad)`.
  Raw 1 Гц + continuous aggregates: `measurements_30s`, `_1m`, `_3m`, `_5m`, `_10m`, `_15m`.
  Сжатие сегментов старше 7 дней.
- `waveforms`: осциллограммы при сработке — `event_id, sample_ts, ia, ib, ic, ua, ub, uc`
  (симулятор синтезирует 20-периодную запись при коде аварии «КЗ»).
- `events`: `time (мс), object_id, cls (alarm|abnormal|state|operator), priority
  (critical|high|low|info), code, message, value, setpoint, acked, acked_by, acked_at`.
- `operator_actions`: `time, username, action, object_name, result, details` — все действия
  диспетчера, включая неудачные попытки ТУ (требование ТЗ 3.3.2, примечание).

### 5.3. Валидация и качество данных (ТЗ 3.1, 3.3.1)

Правила в collector, результат — флаг quality:

| Условие | quality | Индикация |
|---|---|---|
| В физических границах и техно-границах | good | обычная |
| Выход за технологические границы (уставки) | suspect | оранжевый + ⚠️ |
| Выход за физические границы | bad | оранжевый + ⚠️ |
| Логическая несовместимость дискрет (невалидный код состояния, «вкл»+«откл» одновременно, ток при отсутствии напряжения) | bad | оранжевый + ⚠️ |
| Потеря связи с контроллером (таймаут опроса) | suspect у всех точек | оранжевый + ⚠️ |

Событие «ненормальный режим» создаётся при переходе quality good→suspect/bad (без
дублирования, пока значение не вернётся в норму).

## 6. Уровень сбора данных

### 6.1. Контракт адаптера (точка замены симуляции)

```python
class BaseAdapter(abc.ABC):
    async def connect(self) -> None: ...
    async def close(self) -> None: ...
    async def read_batch(self, points: list[Point]) -> list[Reading]: ...
    async def write_command(self, action: int, point: Point | None = None) -> CommandResult: ...
    async def health(self) -> bool: ...
```

- MVP: `ModbusSimAdapter` (TCP к симулятору).
- Будущие: `Iec104Adapter`, `Iec61850MmsAdapter` (libiec61850), `DlmsAdapter`, `OpcUaAdapter`
  (asyncua). Добавление нового протокола = новый класс + регистрация в конфиге.
- Потеря связи → исключение от read_batch → collector помечает все точки suspect (§5.3).

### 6.2. Карта регистров симулятора (holding registers)

| Адрес | Назначение | Кодирование |
|---|---|---|
| 0 | U, В | целое |
| 1 | I, А | целое |
| 2 | P, кВт | целое |
| 3 | Q, кВАр | целое |
| 4 | THDu, % | ×10 |
| 5 | THDi, % | ×10 |
| 6 | PF, о.е. | ×100 |
| 7 | Состояние вводного выключателя | 0=откл, 1=вкл, 2=местное управление |
| 8 | Код аварийной ситуации | 0=нет, 1=КЗ(МТЗ), 2=перегрузка, 3=перенапряжение |
| 9 | Отложенная команда ТУ | 0=нет, 1=вкл, 2=откл (исполняется с задержкой актуатора) |

### 6.3. Сценарный движок симулятора

- Базовый режим: суточный профиль нагрузки (медленный дрейф P) + шум; U ≈ 230 В,
  THDu ≈ 2,5–4 %, THDi ≈ 6–8 %, PF ≈ 0,95–0,98.
- Инъекции (запускаются из Admin UI или тестами, с длительностью):
  - **КЗ (код 1):** ток ×6, PF падает, через 0,5 с выключатель отключается («сработка МТЗ»),
    синтезируется осциллограмма.
  - **Перегрузка (код 2):** ток и мощность ×2,2, THDi +4 % → suspect по I, THDi.
  - **Перенапряжение (код 3):** U → 460 В → suspect по U.
  - **Отказ привода:** команда ТУ не исполняется в срок → «неопределённое» состояние,
    оранжевый индикатор, ТУ завершается таймаутом.
  - **Потеря связи:** остановка сценарного цикла → таймауты опроса → suspect везде.
- Задержка исполнения ТУ-команды конфигурируется (MVP: 1–3 с) — для проверки окна
  ожидания смены состояния.

## 7. Телеуправление (ТЗ 3.3.2 — полный алгоритм)

1. **Выбор объекта:** ПКМ по аппарату на мнемосхеме в режиме ТУ → объект мигает синим,
   открывается диалог ТУ.
2. **Проверка блокировок:** программные (таблица interlocks: например «аварийный режим —
   ТУ запрещено», «земляная нож включён — операция запрещена») + ответ адаптера. При
   блокировке кнопка исполнения неактивна, сообщение «Телеуправление запрещено» + тип
   блокировки.
3. **Выбор команды:** «Включить»/«Отключить» — визуальное выделение выбранного действия.
4. **Подтверждение:** таймаут выбора **10 с**, по истечении выбор сбрасывается
   автоматически (токен select-operation с expires_at).
5. **Исполнение:** ожидание изменения состояния объекта **5 с** (опрос live-кэша 0,25 с).
   Успех → индикация по динамической схеме + сообщение об успехе; таймаут → команда
   сбрасывается, сообщение о неуспехе, состояние помечается «неопределённым».
6. **Аудит:** все шаги (включая неудачные) — в `operator_actions` с учёткой диспетчера.

API: `POST /api/commands/select` (dispatcher+) → токен; `POST /api/commands/operate`
(dispatcher+, токен) → результат. Роли viewer ТУ недоступно (403).

## 8. События и журналы (ТЗ 3.3.3)

Приоритеты и цветовое кодирование (ISA-18.2):

| Приоритет | Цвет | До квитирования | Пример |
|---|---|---|---|
| critical | ярко-красный, мигающий | мигает | Сработка МТЗ, аварийное отключение |
| high | оранжевый/жёлтый, мигающий | мигает | Перегрузка, перенапряжение |
| low/info | светло-жёлтый/синий | мигает | Изменение состояния, вход в систему |

Окно сообщений внизу экрана (все зоны): поля дата/время (мс), приоритет (цвет),
объект, описание, значение/уставка, кнопка «Подтвердить» (квитирование), ссылка
«Мнемосхема» (переход к схеме объекта). Порядок: активные неквитированные сверху вниз
по приоритету, затем квитированные; мигание прекращается после квитирования.

Журналы (раздел «Журналы», выборка из раздела «Выбор»): журнал действий диспетчера,
журнал аварийных событий, журнал ненормальных режимов, журнал всех событий. Из строки
аварии с осциллограммой — просмотр записи по клику.

## 9. Пользовательские интерфейсы (одна SPA, три зоны)

Технически: один Vite-проект, ленивая загрузка зон, ролевой guard на маршрутах.
Права проверяются на бэкенде для каждого запроса — роутинг лишь удобство.

### 9.1. `/arm` — АРМ диспетчера (роли: dispatcher, viewer — просмотр без ТУ)

Экраны:
1. **Мнемосхема (главная):** светло-серый фон; однолинейная схема ТП (ввод 10 кВ,
   трансформатор, секция 0,4 кВ, фидеры) с интегральными показателями (кВт, кВАр, А, В)
   и состоянием аппаратов. ПКМ по объекту с вложенностью — переход на детальную схему;
   ЛКМ — всплывающее окно детальных показателей объекта.
2. **Динамическая индикация кабельных линий:** под напряжением — сплошная тёмно-серая;
   обесточена — пунктирная блёкло-серая; неопределённое — сплошная оранжевая + ⚠️ у
   привязанных значений; аварийное — мигающая ярко-красная.
3. **Динамическая индикация аппаратов:** вкл — заполненный зелёный квадрат; откл — пустой
   квадрат; местное управление — квадрат с буквой «Р»; неопределённое — заполненный
   оранжевый + ⚠️; аварийное — заполненный мигающий красный.
4. **Режим ТУ** (только dispatcher): алгоритм §7.
5. **Аларм-бар** (низ экрана): §8.
6. **Навигация:** статичная панель, кнопки Назад/Вперёд (история переходов), «Домой»,
   правило 3-кликов, прямой переход из строки события к мнемосхеме.

### 9.2. `/mes` — MES-уровень (роли: dispatcher, admin; viewer — обзор без деталей)

Верхняя шапка: «Мнемосхема» · «Выбор» · «Журналы» · «Аналитика» · «Отчёты» · «PAS»
(PAS в MVP — экран-заглушка «требуется прямая интеграция с ПО SATEC»).

1. **Общая картина:** KPI-плитки (суммарные P/Q, токи, напряжения, число активных
   неквитированных алармов по приоритетам), топ критических объектов по потреблению.
2. **Выбор (общее окно для Журналов/Аналитики/Отчётов):** иерархическое дерево объектов
   (критические объекты помечены), параметры (флажки), интервалы: скользящие 5/10/15/30 мин
   (реальное время, только телеизмерения), ретроспектива 8/12 ч, произвольный диапазон
   дата/время; интервал усреднения 0,5/1/3/5/10/15 мин.
3. **Аналитика:**
   - профили показателей (P, Q, PF, U/I по фазам) — раздельная/совмещённая визуализация
     (до 3 осей Y), цвет по показателю/фазе;
   - профили ПКЭ: THDu/THDi по фазам, несимметрия, I0, К-фактор;
   - пороговые линии на всех графиках (цвета и значения задаёт пользователь);
   - зум/детализация выделением мышью (мгновенная подгрузка сырых точек без сжатия);
   - Max/Min/среднее для каждой переменной;
   - гистограммы (мода, медиана, среднее, σ, 3σ, Cpk при уставках);
   - контрольные карты Шухарта и кумулятивных сумм (CUSUM);
   - эмпирические функции распределения ПКЭ с процентом выхода за границу;
   - 2D-тепловые карты (THDi/P/THDu; I/время/отклонение напряжения);
   - надёжность: гистограмма частоты аварий по объектам и интервалам;
   - ограничение ≤ 4–6 кривых на поле графика (защита от визуального шума).
4. **Отчёты:** техучёт (энергия/мощность), ПКЭ, аварийность; экспорт CSV/Excel
   (PDF — опционально через LibreOffice).

### 9.3. `/admin` — Admin UI (только роль admin)

1. **Пользователи:** список, создание, смена роли (admin/dispatcher/viewer), деактивация,
   сброс пароля. Все операции — в журнал.
2. **Справочники:** дерево объектов (CRUD), теги (уставки/границы), ТУ-блокировки.
3. **Журнал действий операторов** — просмотр/фильтрация.
4. **Пульт симулятора (учебная фича, только в MVP):** запуск инъекций (КЗ, перегрузка,
   перенапряжение, отказ привода, потеря связи), настройка задержки актуатора. При замене
   симулятора реальным оборудованием раздел скрывается конфигурацией.

## 11. Безопасность и локальность

- Все сервисы биндятся на адрес LAN-интерфейса (не 0.0.0.0 в публичные сети); интернет
  системе не требуется.
- Windows Firewall: входящие правила только для приватного профиля; порты: web 8000,
  modbus 5020 (только localhost/LAN).
- Обязательная аутентификация; роли admin/dispatcher/viewer; RBAC на бэкенде.
- Пароли PBKDF2 (120k итераций, индивидуальная соль); JWT HS256, срок жизни сменяемый.
- Аудит: журнал действий оператора (включая неудачные ТУ), журнал входов.
- Бэкапы: pg_dump БД + копия конфигов по расписанию (Task Scheduler, ночью, хранить N копий).
- HTTPS с самоподписанным сертификатом — опция (на изолированной LAN допустим HTTP для MVP).
- Секреты (jwt_secret, пароль БД) — в .env вне репозитория.

## 12. Развёртывание на Windows-ноутбуке

1. Установить PostgreSQL 16 (+ TimescaleDB), создать БД `titan`.
2. `uv sync` backend; `npm install && npm run build` frontend (статика отдаётся FastAPI).
3. Конфиг `.env`: строка БД, bind-адрес, секреты.
4. Запуск MVP: одна команда `uv run uvicorn titan.api.app:app` (embedded-режим:
   симулятор + коллектор стартуют вместе с API). Разнесённый режим: отдельные процессы
   `python -m titan.simulator`, `python -m titan.collector`, web-api.
5. Автозапуск: NSSM-службы или Task Scheduler; бэкап — задача планировщика.

## 16. Журнал реализации и изменений

Хронология работ по срезам §14 и все отклонения/дополнения к проекту.
Правило: каждое изменение кода после версии 1.0 фиксируется здесь
(дата · срез/компонент · суть · затронутые требования ТЗ).

### M0 — скелет (выполнено)
- Монорепо `titan-energy/{backend,frontend,docs}`; uv-окружение; pytest-каркас.
- **Отклонение от §3:** pymodbus закреплён на **3.9.2** — версии 3.12+ переделали
  API (ModbusSlaveContext → ModbusDeviceContext, SimData/SimDevice) несовместимо
  с проектом. Обновление потребует переписать симулятор.
- **Технический факт:** сервер pymodbus 3.x смещает адреса на +1 (`getValues:
  address += 1`) — движок пишет в datastore по адресу `addr + 1`.

### M1 — сбор + БД + журналы (выполнено)
- Модели: `measurements`, `events` (§5.2). SQLite (aiosqlite) вместо Postgres/
  TimescaleDB на старте — миграция = смена `database_url` (допущено §2.3).
- Коллектор: опрос 1 Гц → декодирование → валидация → батч-запись в БД;
  при потере связи записи нет (в архиве нет подставных нулей — требование
  достоверности, ТЗ 3.1).
- Генератор событий: код аварии → `alarm` (с уставкой), выход за техно-границы
  → `abnormal` **без дублирования** до возврата в норму, возврат → `state`/info (§5.3, §8).
- **Правка логики валидации (21.11):** обесточенное состояние (BREAKER=0) —
  нулевые U/I/P/Q = `good` (штатный режим после сработки защиты, а не «потеря
  напряжения»). До правки U=0 после КЗ висел оранжевым suspect — некорректно.
  *(ТЗ 3.3.1: неопределённое состояние ≠ обесточено.)*

### M2 — auth/RBAC (выполнено)
- PBKDF2-HMAC-SHA256 (120k, соль), JWT HS256 (§11); иерархия ролей
  viewer < dispatcher < admin; `require_role()` — права на каждый запрос (§9).
- Модели `users`, `operator_actions` — аудит ВСЕХ действий, включая неудачные
  попытки входа/ТУ (ТЗ 3.3.2, примечание).
- Автосоздание `admin/admin` при пустой БД (пароль через `TITAN_ADMIN_PASSWORD`
  в проде; смена через Admin UI). Защита от само-деактивации единственного админа.
- **SQLite → WAL-режим + busy_timeout 30 с:** коллектор и API пишут одновременно
  без «database is locked» (было: падения при параллельной записи журналов).

### M3 — SPA + Admin UI (выполнено)
- React + TS + Vite, TanStack Query, Zustand, react-router (§9, §3).
- Страницы: логин, телеметрия (плитки 1 Гц, цвет = quality), журналы
  (4 раздела ТЗ, квитирование), администрирование (users CRUD + журнал
  операторов), пульт симулятора (5 кнопок инъекций — учебная фича MVP).
- **Багфикс:** SPA-catch-all маршрут объявлен ПОСЛЕ всех `/api/*` — иначе
  перехватывал их (браузер получал HTML вместо JSON на `/api/live`).
- **Багфикс:** CSS-комментарии `//` → `/* */` (lightningcss Vite падал).
- **Ужесточён сценарий «перегрузка»** (×2.2 → ×6, THDi +4 → +12): прежний не
  выходил за техно-границы → suspect не появлялся, демонстрация была пустой.
- **Изоляция тестов:** `TITAN_TEST_DB=1` (conftest) — временная БД на процесс;
  **порт Modbus тестов = 5021** (21.11) — иначе тестовый коллектор подключался
  к живому серверу разработчика на 5020 и ТУ-тесты падали (504).

### M4 — мнемосхема, ТУ, осциллограммы (выполнено)
- Двухшаговый ТУ (§7): select (блокировки → токен 10 с) → operate (write в
  регистр 9, ожидание смены BREAKER 5 с, поллинг 0.25 с). Блокировки:
  «аварийный режим», демо-«P > 300 кВт». Полный аудит шагов.
- Осциллограммы (ТЗ: архив при сработках): при КЗ синтез 20 периодов,
  1 кГц, 6 каналов (апериодическая составляющая, просадка Ua); таблица
  `waveforms`; просмотр `GET /api/waveforms/{id}`.
- SVG-мнемосхема: индикация по ТЗ 3.3.1 (сплошной/пунктир/оранжевый/мигающий
  красный; квадраты вкл/откл/«Р»/неопределённый/аварийный).
- Аларм-бар ISA-18.2: неквитированные по приоритету, мигание до ack.
- **Багфикс (21.11):** `pointer-events="bounding-box"` на группе выключателя —
  при `fill="none"` (отключён) клики «проваливались» сквозь квадрат, ПКМ не
  работал. *(ТЗ 3.3.2: ТУ должно работать в любом состоянии аппарата.)*
- **Доработка comm_loss (21.11):** потеря связи теперь **восстанавливается**
  после истечения сценария (`server.shutdown()` → ожидание → перезапуск
  сервера). Раньше сервер умирал навсегда — ТУ не работало до перезапуска.
  *(ТЗ 3.3.1: неопределённое состояние — временное, связь возвращается.)*
- **UI-полировка (21.11):** ошибки ТУ распаковываются из JSON (`detail`)
  в человекочитаемый текст диалога.

### M5 — MES-аналитика (выполнено)
- Математика (`analytics/stats.py`, TDD): статистика ряда, скользящее среднее,
  гистограмма (мода/медиана/σ/3σ), Шухарт (CL ± 3σ + индексы выхода),
  CUSUM (§9.2 «Анализ»).
- API: series/histogram/shewhart/cusum + экспорт CSV/xlsx (openpyxl) — ТЗ 3.1.
- **Доработка (21.11): автообновление графиков** — refetch 5 с (гистограмма 15 с),
  чекбокс «Обновление 5 с»; перерисовка через `setOption` без пересоздания
  (зум сохраняется). *(ТЗ раздел 4: «последние 5/10/15/30 минут — реальное
  время, скользящее окно, тренд».)*
- **Вне MVP по §1, но реализовано:** ряды/гистограммы/Шухарт/CUSUM/экспорт.
  Не реализовано из ТЗ (подтверждаем отложенное): тепловые карты 2D, ЭФР,
  КПЭ удельных расходов, PAS.

### M6 — эксплуатация (выполнено)
- Бэкапы: копия SQLite с timestamp + ротация keep=7 + restore (`backup.py`,
  CLI `backup_cli.py`; тесты на реальном файле). Task Scheduler/NSSM — docs/DEPLOY.md.
- README запуска с нуля (~10 мин, критерий M6 ≤ 30 мин выполнен).
- Firewall: правило только для приватного профиля (§11).

### Глобальные доработки (21.11, вне срезов)
- **Время в GMT+3** (требование заказчика): хранение UTC, отдача клиенту
  в таймзоне диспетчера (`timeutil.fmt_iso_ms`, смещение настраивается
  `TITAN_TZ_OFFSET_HOURS`, по умолчанию 3). Покрыто: журналы, аларм-бар,
  квитирования, действия операторов, история, аналитика, осциллограммы,
  экспорт CSV/Excel. *(ТЗ 3.3.3: время с точностью до мс; время должно
  совпадать с часами диспетчера для оценки последовательности срабатываний.)*
- **Руководство пользователя** (`docs/USER_GUIDE.md`): все разделы UI +
  сценарий демонстрации + FAQ.
- **Порядок тестов/состояния:** conftest сбрасывает live-кэш коллектора,
  ТУ-токены и движок симулятора после каждого теста (инъекция КЗ из одного
  теста не «перетекает» в следующий — блокировка «аварийный режим» ложно
  срабатывала на ТУ-тестах).

- **Багфикс «чёрный экран» (23.11):** при действиях с журналом UI мог уйти
  в чёрный экран до перезагрузки страницы — непойманная ошибка рендера React
  уносила весь root. Добавлен ErrorBoundary (`frontend/src/ErrorBoundary.tsx`)
  на каждую страницу и аларм-бар: падение одного блока показывает карточку
  ошибки с кнопкой «Повторить», остальной UI и навигация продолжают работать.
  *(ТЗ 3.3 «Навигация»: устойчивость интерфейса диспетчера.)*

### Многоуровневая мнемосхема (23.11, вне срезов)

Реализована трёхуровневая навигация по заводу (решение согласовано с
заказчиком: 3 уровня, 4 шаблона аварий, ПКМ-создание + пульт):

- **Дерево завода** (`backend/titan/simulator/factory.py`):
  Завод → ТП-1, ТП-2 → ввод QF1 / трансформатор / секция / 4 фидера
  («Насосная», «Станочный цех» и др.). Каждая ТП — отдельное Modbus-
  устройство (unit_id 1, 2).
- **Симулятор multi-object:** движок на каждую ТП; точечные инъекции
  на объекты; регистр 20 = индекс фидера-владельца аварии; «обрыв
  кабеля» на вводе = потеря связи всей ТП (вторая ТП работает).
- **Коллектор:** live-кэш ключуется «объект:точка» (`tp1_f2:I`),
  опрос ТП независимый; события привязаны к объекту («ТП-1, Ф-2»).
- **API:** `POST /api/sim/fault?object_id=...` (точечная инъекция),
  `GET /api/objects/tree`.
- **Мнемосхема (3 уровня, хлебные крошки, правило 3 кликов):**
  Уровень 0 «Завод» — плитки ТП, агрегированный статус снизу вверх
  (авария → красная мигающая, suspect → оранжевая), интегральные P/I/U;
  Уровень 1 «ТП» — однолинейная схема с per-object значениями фидеров;
  Уровень 2 «Объект» — детальная схема фидера + плитки показателей.
- **Пульт симулятора:** выбор объекта в дереве + 4 шаблона (КЗ/МТЗ,
  перегрузка, перенапряжение, обрыв кабеля) + длительность 3–30 с.
- Проверено вживую: КЗ на Ф-2 ТП-1 → аларм «ТП-1, Ф-2» с уставкой МТЗ,
  мигание плитки ТП-1 на уровне завода, «Обесточено» после сработки.

### Исправление ключевого сценария демонстрации (24.11)

Три бага, найденных при прогонке демо:

1. **ПКМ-меню не содержало «Потерю ввода 110 кВ»** (сценарий был только в
   пульте симулятора). Меню теперь зависит от типа объекта: у вводов 110 кВ
   первым пунктом — line_loss_110 с длительностью 25 с (чтобы успеть
   показать переброс). Попутно: ПКМ больше не открывает диалог ТУ вместе
   с меню (двойное действие сбивало с толку).
2. **Секционный QF не отключался после восстановления линии** — симулятор
   не соблюдал собственные правила. Теперь: линия «починилась» → ввод
   включается автоматически (аналог АПВ) → СВ отключается автоматически
   (параллельная работа вводов запрещена — те же правила, что проверяет
   ТУ-блокировка). Технически: СВ живёт в движке unit 2, сброс через
   колбэк on_line_restored.
3. **Карточка Секционного QF без показаний** (у аппарата нет своей
   телеметрии) — теперь показывает контекст переброса: U/I/P обеих секций
   с признаком «ОБЕСТОЧЕНА»/значения, состояние словами
   «ВКЛЮЧЕН — секции соединены (переброс)».

E2E полного цикла (после фиксов): авария (BREAKER=0, U=0, FAULT=5) →
ТУ СВ (переброс: U=228 В, P=153 кВт, СВ=1) → восстановление линии через
20 с (BREAKER=1, U=228, **СВ=0 автоматически**). Регресс: 28+31=59 passed.

### Модель учебной ПС 110/10 кВ (23.11, по MVP_SCADA_Denis.docx)

Реализована однолинейная схема реальной понизительной подстанции

  запрет параллельной работы вводов; запрет СВ при двух обесточенных;
  ТУ на СВ разрешено именно при аварии «потеря 110 кВ» (код 5),

- **Мнемосхема** перестроена под рисунок из документа: уровень «Схема ПС» —
  два плеча сверху, шины внизу, СВ в центре, 8 фидеров с токами;
  подписи «от ввода №N / запитана через СВ / ОБЕСТОЧЕНА» — расчёт
  запитанности по связности схемы.
- **Живой сквозной тест пройден**: инъекция line_loss_110 → аларм critical →
  ТУ «Секционный QF» → исполнено → секция I запитана от плеча Б (U=228, P=135).

### Миграция на PostgreSQL 16.10 (23.11, вне срезов)
- **Решение:** SQLite → чистый PostgreSQL 16.10 (EDB-сборка, asyncpg-драйвер).
  TimescaleDB на Windows **отложена**: DLL 2.17.2/2.32.1 стабильно конфликтуют
  с EDB-сборкой PostgreSQL («loader version out-of-date», «procedure not found» —
  issue #6809/#6830 upstream). Community-статус TimescaleDB на Windows.
- **План перехода на TimescaleDB:** Linux-сервер или Docker (официально
  поддерживаемые платформы) — конфиг кода уже готов к смене URL.
- Усреднения реализованы SQL GROUP BY по time_bucket (PostgreSQL native),
  для текущих объёмов (9 точек/с ≈ 780К строк/сутки) производительности
  хватает с запасом; сжатие и continuous aggregates — после переезда.
- Данные: база `titan`, пользователь `titan_app` (пароль в config, прод: .env).
- **Проверено вживую:** 5 таблиц созданы автоматически create_all, телеметрия
  1 Гц пишется, аналитика/история через API работают. 47/47 тестов
  (тесты на изолированной SQLite, прод на PostgreSQL).
