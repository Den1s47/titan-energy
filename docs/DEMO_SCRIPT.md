# ПАК «Титан-Энергия» — сценарий демонстрации директору

> Распечатай или открой на планшете. Тайминг: **15–20 минут** вместе с вопросами.
> Сервер: `cd C:\Users\HP\HermesProjects\titan-energy\backend && uv run uvicorn titan.api.app:app --host 127.0.0.1 --port 8000` → открой http://127.0.0.1:8000

---

## 1. Что это за продукт (скажи в первые 30 секунд)

Полноценный прототип **EMS/SCADA+MES системы мониторинга качества электроэнергии**
по ТЗ ООО «ЭНСИТЕХ» — не слайды, а работающая программа:

- **SCADA-уровень**: сбор телеметрии 1 Гц по настоящему **Modbus TCP**, мнемосхема
  с динамической индикацией, телеуправление с двухшаговым подтверждением,
  журналы событий по ISA-18.2, осциллограммы при КЗ.
- **MES-уровень**: аналитика — тренды за сутки/неделю, карты Шухарта и CUSUM,
  гистограммы, КПЭ (доступность, аварийность), экспорт CSV/Excel.
- **Объект** — учебная понизительная подстанция 110/10 кВ (два ввода 110 кВ,
  трансформаторы T1/T2, две секции 10 кВ по 4 фидера, секционный выключатель).
  «Железо» заменено симулятором уровня протокола — подключение реального
  оборудования меняется **только конфигурацией адаптера**, код выше не трогается.

## 2. Архитектура (нарисуй на бумаге или покажи схему из спецификации §4)

```
[Оборудование / Симулятор Modbus TCP :5020, 2 устройства unit 1/2]
        │  регистры 0–12 (U, I, P, Q, THDu, THDi, PF, BREAKER, FAULT, CMD, СВ)
        ▼
[Collector — опрос 1 Гц] ──► оценка качества (good/suspect/bad) ──► генератор событий ISA-18.2
        │                                                        │
        ▼                                                        ▼
[PostgreSQL: measurements (~700 тыс. записей), events, users, actions]
        ▲
        │ REST API (FastAPI, JWT, роли RBAC viewer/dispatcher/admin)
        ▼
[SPA-фронтенд (React+TypeScript+ECharts): мнемосхема, журналы, аналитика, админка, пульт]
```

Ключевые решения (упомяни, звучит уверенно):
- **Слои изолированы**: симулятор ↔ адаптер ↔ коллектор ↔ API ↔ UI. Меняем железо —
  не трогаем верхние слои (спецификация §2.3, §13).
- **Безопасность**: PBKDF2-хэши паролей с солью, JWT, RBAC на каждый эндпоинт,
  блокировки ТУ на уровне бэкенда (не только UI!), аудит действий.
- **Данные**: время UTC в БД, GMT+3 в интерфейсе; параметризованные запросы
  (SQL-инъекции не проходят — проверено пентестом).

## 3. Маршрут демонстрации (по порядку, каждый шаг = экран)

### Шаг 1. Мнемосхема — главный экран (2 мин)
Открывается **сразу полная однолинейная схема ПС 110/10** во всю ширину.

Покажи: вводы 110 кВ, Q-110, трансформаторы, вводы 10 кВ **с живыми показаниями**,
шины секций, секционный QF в центре, 8 фидеров с токами.

- Цвета = состояния (легенда под схемой): зелёный — включён, серый/пустой —
  отключён, красный мигающий — авария, пунктир — обесточено.
- **Клик по любому узлу** → карточка объекта справа (или слева, если кликал справа):
  состояние словами, 7 показателей, кнопка ТУ.
- Кнопка **«☰ Объекты»** → дерево всей ПС; аварийные объекты красные прямо в дереве.

### Шаг 2. Ключевой сценарий: потеря ввода 110 кВ → переброс (4 мин) ⭐
Это центральный номер. Провалидируй блокировки и автоматический аларм.

1. ПКМ по **«Ввод 110 кВ №1»** → «Создать аварию» → сценарий
   **«Потеря ввода 110 кВ»**, длительность 25 с.
2. Что произойдёт (дай посмотреть 3–5 секунд):
   - вводный выключатель Q-110 №1 гаснет → серый, кабель пунктир,
   - секция I **ОБЕСТОЧЕНА**, плитка плеча А мигает,
   - баннер сверху: «⚡ Потеря ввода 110 кВ» + подсказка человеческим языком:
     *«Перебросьте питание: включите секционный QF»*,
   - в журнале появилась критическая запись.
3. Восстанови питание через **телеуправление**: клик по **Секционному QF**
   (или ПКМ → ТУ) → диалог двухшагового ТУ:
   - выбери «Включить» → подтверждение с обратным отсчётом 10 с → «Исполнить»,
   - результат: «Команда исполнена», СВ зелёный,
   - **на схеме видно**: секция I снова под напряжением — «через СВ»,
     ток и мощность вернулись. Переброс выполнен.
4. Объясни **блокировки** (это любят): СВ не включится при прочих авариях,
   запрещена параллельная работа вводов, нельзя включить СВ при двух
   обесточенных секциях. Блокировки на бэкенде — их не обойти из UI.

### Шаг 3. Журналы (1–2 мин)
Сайдбар → «Журналы».
- Записи ISA-18.2 с приоритетами (critical/high/low), объектом, значением и уставкой.
- **Квитирование** (кнопка «Подтвердить» у dispatcher+) — оператор подтверждает,
  что увидел аварию.
- Клик по объекту в строке аларма → мнемосхема раскрывает этот узел.
- Осциллограмма при КЗ (записывается автоматически).

### Шаг 4. Аналитика (3 мин)
Сайдбар → «Аналитика».
- Период: выбери **«Сутки»** — наверху КПЭ: **доступность %, число событий,
  критических аварий** (по живой базе — там уже сотни тысяч записей).
- Временной ряд с автомасштабом; **вертикальные пунктиры — аварии из журнала
  прямо на графике**: «вот КЗ — и вот как просела мощность».
- Чекбокс «Сравнить с arm2_incomer:P» — ввод №1 vs №2 на одном графике.
- Карта Шухарта: подписи порогов с числами (UCL = 242.3), зона нормы подсвечена;
  CUSUM; гистограмма с модой/медианой.
- Внизу — **экспорт CSV/Excel** (скачай и покажи файл — «инженерный отчёт»).

### Шаг 5. Пульт симулятора и роли (2 мин)
- «Пульт симулятора» (только admin): дерево объектов + 4 шаблона аварий +
  ползунок длительности. Это наш «стенд»: вместо реального железа.
- «Админка» (только admin): пользователи, роли; **аудит входов** —
  кто, когда, что менял.

## 4. Что программа «умеет» — шпаргалка ответов на вопросы

| Вопрос директора | Ответ |
|---|---|
| «Это работает с настоящим оборудованием?» | Протокол настоящий — Modbus TCP. Симулятор закрыт адаптером; для реального ПС меняется только конфигурация подключения. |
| «Почему подстанция 110/10?» | Модель реальной понизительной ПС из вашего документа (MVP_SCADA_Denis) — с двумя вводами и секционным выключателем: типовой объект, на нём виден главный сценарий переброса. |
| «Что делать при аварии 3 часа ночи?» | Мнемосхема сразу показывает ЧТО случилось человеческим языком и ПОДСКАЗКУ оператору («включите секционный QF»). Мигает только авария, подсказка не мигает. |
| «Сколько данных держит?» | PostgreSQL; в прототипе уже ~700 тыс. измерений. Аналитика за сутки/неделю агрегируется автоматически. |
| «Кто что может?» | RBAC: viewer — только смотреть; dispatcher — квитирование и ТУ; admin — пользователи и пульт. Все действия логируются. |
| «Насколько это безопасно?» | Пароли — PBKDF2, сессии — JWT, каждая проверка — на бэкенде. Проводили пентест: SQLi, подделка токенов, аномальные параметры — отсекаются. |
| «Сколько до промышленной версии?» | Документация и архитектура готовы к масштабированию: реальное оборудование, TimescaleDB для больших объёмов (план в спецификации), уведомления. |

## 5. Технические цифры (если спросят «а внутри?»)

- Backend: **Python + FastAPI**, PostgreSQL 16 + SQLAlchemy async, pymodbus.
- Frontend: **React + TypeScript**, ECharts, сборка Vite.
- Тесты: **59 автотестов** (pytest) — API, авторизация, ТУ, аналитика, симулятор, бэкапы.
- Симулятор: 2 устройства Modbus TCP, 7 сценариев аварий (КЗ, перегрузка,
  перенапряжение, обрыв кабеля, потеря 110 кВ).
- Документация: спецификация с историей разработки (§16 — журнал изменений),
  руководство пользователя, README.

## 6. Если что-то пойдёт не так

- **Страница пустая/старая** → Ctrl+Shift+R (жёсткое обновление кэша).
- **Сервер не отвечает** → перезапусти командой из шапки; проверь порт 8000.
- **ТУ выдало «запрещено»** → это блокировка, не баг: показывает, что защита работает.
  Отключи причину (например, дождись окончания аварии) и повтори.
- **График пустой** → выбери другой период (данные идут постоянно).
- Совсем всё сломалось → демо можно продолжить на истории: в базе сотни тысяч
  точек и журналы за дни — аналитика и архивы работают без «живого» железа.
