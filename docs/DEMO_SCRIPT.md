## 1. Что это за программа — простыми словами

Представь обычную подстанцию в посёлке или на заводе. К ней приходят две линии
высокого напряжения 110 киловольт (кВ), два больших трансформатора понижают
напряжение до 10 кВ, и дальше электричество расходится по 8 линиям к потребителям
(насосная, вентиляция, станочный цех...).

**Проблема, которую решает программа**: сейчас за такой подстанцией следит человек —
он смотрит на стрелки приборов, ездит проверять оборудование, узнаёт об аварии
по звонку. Это медленно и опасно.

**Наша программа** — это «глаза и руки» диспетчера:
- **Глаза** — она каждую секунду опрашивает оборудование и рисует на экране
  живую схему: что включено, что выключено, где авария;
- **Руки** — оператор может щёлкнуть выключателем прямо с экрана
  (это называется «телеуправление», сокращённо ТУ);
- **Память** — всё, что происходило, сохраняется в базу данных, и можно
  построить график за сутки, посчитать статистику, скачать отчёт.

Такие системы называются **SCADA** (диспетчерское управление и сбор данных) +
**MES** (аналитика производства). Мы делаем прототип такой системы по
техническому заданию ООО «ЭНСИТЕХ».

**Важная честная оговорка для демо**: к настоящей подстанции мы подключиться
не можем (это опасно и требует оборудования). Поэтому программа общается с
**симулятором** — программой-«фальшивой подстанцией», которая ведёт себя
как настоящая: отдаёт те же сигналы, по тому же протоколу. Это как тренажёр
у пилота: всё настоящее, кроме самолёта. Когда захотят подключить реальную
подстанцию — в конфигурации меняется адрес подключения, и всё остальное
работает без изменений.

## 2. Архитектура: из чего состоит и почему именно так

Архитектура — это «план здания»: из каких частей состоит программа и как они
разговаривают между собой. Вот наш план:

```
┌────────────────────────────────────────────────────────────┐
│ УРОВЕНЬ 1: ОБОРУДОВАНИЕ                                    │
│ Симулятор подстанции (Modbus TCP, порт 5020)               │
│ «Фальшивая подстанция»: 2 устройства (unit 1 и 2)          │
└──────────────────┬─────────────────────────────────────────┘
                   │ протокол Modbus TCP (промышленный стандарт)
                   ▼
┌────────────────────────────────────────────────────────────┐
│ УРОВЕНЬ 2: КОЛЛЕКТОР                                       │
│ Каждую секунду спрашивает у оборудования показания,        │
│ оценивает их качество, замечает аварии, пишет в базу       │
└──────────────────┬─────────────────────────────────────────┘
                   │ сохраняет данные
                   ▼
┌────────────────────────────────────────────────────────────┐
│ УРОВЕНЬ 3: БАЗА ДАННЫХ PostgreSQL                          │
│ measurements (~700 000 измерений), events (события),       │
│ users (пользователи), operator_actions (аудит)             │
└──────────────────┬─────────────────────────────────────────┘
                   │ читает/пишет через API
                   ▼
┌────────────────────────────────────────────────────────────┐
│ УРОВЕНЬ 4: API-СЕРВЕР (FastAPI)                            │
│ «Официант»: принимает запросы от экранов, проверяет        │
│ права, отдаёт данные. Никто не лезет в базу напрямую       │
└──────────────────┬─────────────────────────────────────────┘
                   │
                   ▼
┌────────────────────────────────────────────────────────────┐
│ УРОВЕНЬ 5: ЭКРАНЫ (браузер, React)                         │
│ Мнемосхема · Журналы · Аналитика · Админка · Пульт         │
└────────────────────────────────────────────────────────────┘
```

### Почему 5 уровней, а не «всё в одной программе»?

Представь, что программа — ресторан. Можно посадить повара, официанта, кассира
и кладовщика в одного человека — он будет и готовить, и разносить, и считать.
Работать будет, пока клиентов мало. У нас подход другой — каждый занимается
своим делом:

1. **Если сломается экран** — данные продолжают собираться (коллектор не знает
   про экраны вообще). Экран перезапустили — ничего не потеряли.
2. **Если поменяется оборудование** — например, на подстанции поставят реле
   другого производителя — переписывается только «переводчик» (адаптер
   протокола), база, аналитика и экраны не трогаются. Это как заменить
   вилку у прибора, не переделывая сам прибор.
3. **Безопасность**: пользователь никогда не достаёт до базы напрямую — только
   через API-сервер, который проверяет права на каждый запрос. Это значит,
   что зритель (viewer) физически не может выключить выключатель, даже если
   напишет запрос руками.

## 3. Почему выбраны такие технологии (частые вопросы «почему X, а не Y»)

### Почему PostgreSQL, а не SQLite (лайт-версия)?

**SQLite** — это крошечная встроенная база: вся база — один файл на диске,
работает без установки сервера. Отлично подходит: для мобильных приложений,
для маленьких утилит, **для тестов** (у нас она тоже используется в тестах!).

**PostgreSQL** — полноценный сервер баз данных: отдельная программа-служба,
с собственным управлением памятью, пользователями, репликацией.

Почему для боевой системы нужен PostgreSQL:
1. **Одновременный доступ.** У нас пишут данные ВСЕГДА (коллектор каждую секунду),
   а читать могут 5 операторов одновременно + аналитика + отчёты. SQLite при
   одновременной записи «запирает» весь файл целиком — читатели ждут писателя.
   PostgreSQL обслуживает десятки параллельных соединений без блокировок.
2. **Объёмы.** Один объект даёт ~86 400 измерений в сутки (каждая секунда ×
   каждая точка). За год — миллионы строк. PostgreSQL рассчитан на миллиарды
   строк с индексами; SQLite на таких объёмах деградирует.
3. **Надёжность.** PostgreSQL переживает сбой питания без потери данных
   (журнал упреждающей записи WAL). Для системы, которая хранит историю
   аварий, это критично: «а журнал за прошлую неделю пропал» — неприемлемо.
4. **Типизация и целостность.** Строгие типы, проверки на уровне базы,
   транзакции («либо запишется всё, либо ничего»).

А SQLite мы всё равно используем — **в автотестах**: каждый тест получает
свежую одноразовую базу за миллисекунды, тесты не трогают боевую PostgreSQL.
Это лучший из двух миров: разработка — быстро, продакшн — надёжно.

*(Если спросят «а TimescaleDB?» — это расширение PostgreSQL специально для
временных рядов, в плане развития; на Windows его установка упирается в
конфликт библиотек, поэтому отложено на Linux — план есть в спецификации.)*

### Почему Modbus TCP, а не какой-то «свой» протокол?

Modbus — самый старый (1979 год) и самый распространённый промышленный протокол:
прост как «прочитай значение из ячейки №5». Его понимает 90% промышленного
оборудования — счётчики, реле защиты, контроллеры. Выбор Modbus = совместимость
с реальным железом, когда оно появится. Придумать свой протокол было бы
«удобнее», но тогда система подошла бы только к нашему симулятору.

### Почему веб-браузер, а не «программа с установкой»?

1. Ничего устанавливать не надо: открыл браузер — работаешь. Обновление
   версии = перезапуск сервера, у операторов на экранах обновится само.
2. Кроссплатформенность: диспетчер может открыть систему с любого компьютера.
3. Безопасность проще управлять: доступ через сеть, VPN, единая точка входа.

### Почему React, а не просто HTML?

На экране мнемосхемы ~50 объектов, каждый меняет цвет каждую секунду.
React умеет перерисовывать только изменившиеся элементы (а не весь экран) —
без него схема бы «мигала» и тормозила. Плюс TypeScript: ошибки в коде
находятся до запуска, а не в 3 часа ночи на боевом сервере.

### Почему JWT-токены для входа?

После входа сервер выдаёт «пропуск» (токен) с зашифрованной подписью.
Каждый запрос показывает пропуск — сервер проверяет подпись, не храня пароль.
Не надо искать «кто сейчас вошёл» в памяти сервера — сервер можно
перезапустить, а люди продолжат работать.

## 4. Словарь: как читать мнемосхему (термины, которые стоит знать)

Представь подстанцию как водопровод:

| Термин | Что это | Аналогия с водой |
|---|---|---|
| **Ввод 110 кВ №1 / №2** | Две линии, по которым электричество ПРИХОДИТ на подстанцию | Две водопроводные магистрали к дому |
| **Q-110 (выключатель 110 кВ)** | Большой рубильник на входе; умеет разрывать огромные токи | Главный кран на магистрали |
| **T1 / T2 (трансформатор)** | Понижает 110 000 В → 10 000 В | Насос, снижающий давление воды |
| **Ввод 10 кВ №1 / №2** | Выключатель, которым пониженное напряжение подаётся на шину | Кран после насоса |
| **Секция шин I / II** | «Гребёнка», к которой подключаются потребители | Гребёнка полива на участке |
| **Секционный QF (выключатель)** | Соединяет две секции между собой. Нормально ОТКЛЮЧЁН | Перемычка между двумя гребёнками |
| **Фидер (Ф-1…Ф-8)** | Отходящая линия к потребителю со своим выключателем и защитой | Труба с краном на каждую грядку |
| **Ф-1 Насосная, Ф-2 Вентиляция...** | Имена фидеров — что питает каждая линия | «Грядка с помидорами», «грядка с розами» |

### Почему секций две и зачем секционный выключатель — ГЛАВНАЯ ИДЕЯ

Если бы секция была одна, любая авария на входе обесточивала бы ВСЁ. Две
секции + перемычка дают резерв: **при аварии на одной линии 110 кВ половина
потребителей остаётся без света секунды, а не весь посёлок на часы.**

Нормальный режим: Секция I питается от ввода №1, Секция II — от ввода №2,
перемычка (СВ) разомкнута.
Авария: ввод №1 умер → оператор включает СВ → Секция I получает питание
через ввод №2 и перемычку. Это называется **переброс** — и это наш
центральный демонстрационный сценарий.

### Защита (МТЗ) — почему выключатель срабатывает сам

У каждого фидера стоит **защита**: она постоянно сравнивает ток с уставкой
(«разрешённым максимумом»). Ток превысил уставку → защита РАЗРЫВАЕТ цепь сама,
за миллисекунды, не дожидаясь человека. МТЗ = «максимальная токовая защита»,
самый распространённый вид. Уставка — число, которое настройщик задаёт заранее
(у нас: 200 А для вводов, 400 А на КЗ).

## 5. Что происходит на мнемосхеме (читаем экран вместе)

**Мнемосхема** — это живая электрическая схема на экране. Открывается сразу
полная, во всю ширину. Разберём каждый элемент:

### Что нарисовано

```
Ввод 110 кВ №1            Ввод 110 кВ №2
    │                         │
   [Q-110]  ← выключатель   [Q-110]
    │                         │
   (T1)     ← трансформатор (T2)
    │                         │
   [Ввод 10 кВ №1]          [Ввод 10 кВ №2]  ← с цифрами U, I, P
    │                         │
 ═════════ Секция I ═════[СВ]═══════ Секция II ═══════
    │    │    │    │           │    │    │    │
   Ф-1  Ф-2  Ф-3  Ф-4         Ф-5  Ф-6  Ф-7  Ф-8
 Насосная Вентил. Освещ. Резерв Станочн. Компресс. Освещ. Резерв
```

### Как читать цвета (легенда есть и на самой странице)

| Цвет | Значение |
|---|---|
| 🟩 Зелёный квадрат | Аппарат ВКЛЮЧЕН, ток идёт, всё нормально |
| ⬜ Пустой (белый) квадрат | Аппарат ОТКЛЮЧЁН (так задумано или сработала защита) |
| 🟧 Оранжевый | Неопределённое состояние / предупреждение |
| 🟥 Красный МИГАЮЩИЙ | АВАРИЯ — мигает, пока оператор не подтвердит («не квитировано») |
| ─── Сплошная толстая линия | Линия под напряжением |
| ─ ─ ─ Пунктир | Обесточено (напряжения нет) |

Почему мигает ТОЛЬКО авария: по правилам эргономики промышленных экранов
(статья ЭЛТЕКО), мигание — сигнал «требует реакции человека». Всё, что
просто показывает состояние, мигать не должно, иначе оператор перестаёт
замечать мигание вообще.

### Подписи у вводов 10 кВ

У каждого ввода написано живое значение: `U=228 · I=152 · P=171 кВт`.
- **U** — напряжение в вольтах (норма: 220 В ±10%, по ГОСТ 32144-2013),
- **I** — ток в амперах (сколько электричества «течёт»),
- **P** — активная мощность в киловаттах (полезная работа).

У фидеров снизу — их собственные токи. У Секций — подпись источника:
«от ввода №1» или «через СВ» (после переброса) или «ОБЕСТОЧЕНА».

### Баннер аварии и подсказка

При аварии сверху появляется баннер: «⚡ КЗ — сработала МТЗ (плечо А)» и под
ним **подсказка человеческим языком**: «Найдите повреждение линии, включайте
ввод только после проверки». Идея из статьи ЭЛТЕКО: аварии пишутся словами,
а не кодами, и система говорит оператору, ЧТО делать, — иначе в 3 часа ночи
оператор листает инструкции вместо действий.

### Дерево объектов (кнопка «☰ Объекты»)

Та же подстанция в виде списка (дерева): ПС 110/10 → Плечо А → Секция I →
Ф-1…Ф-4. Зачем: на схеме видна топология, а в дереве удобно искать объект
по имени. Объекты с нарушениями **красные прямо в дереве** — видно, ГДЕ
поломки, не открывая уровни.

### Карточка объекта (клик по любому узлу)

Кликнул по трансформатору/фидеру/выключателю → справа (или слева, если кликал
справа — карточка не перекрывает то, по чему кликнул) открывается карточка:
- состояние словами («Включён, работа в норме» / «КЗ — сработала МТЗ»),
- при аварии — подсказка «что делать»,
- 7 показателей: напряжение, ток, мощности, нелинейные искажения (THDu/THDi —
  насколько форма синусоиды «испорчена» современными блоками питания),
  коэффициент мощности (PF — насколько эффективно используется энергия),
- кнопка телеуправления (для аппаратов, которыми можно управлять).

### Плечо А / Плечо Б

Так мы называем две независимые «половины» подстанции: Плечо А = ввод №1 +
T1 + Секция I; Плечо Б = ввод №2 + T2 + Секция II. Слово взято из практики
(«плечо питания»). В коде это arm1/arm2.

## 6. Телеуправление (ТУ) — почему так сложно «просто щёлкнуть»

Включить выключатель с экрана — действие с реальными последствиями. Если
оператор нажал не то или случайно — это обесточивание людей. Поэтому
промышленные системы используют **двухшаговый алгоритм**:

1. **Выбор** («выбрать команду Включить») → сервер проверяет блокировки и,
   если всё чисто, выдаёт ОДНОРАЗОВЫЙ токен на 10 секунд;
2. **Подтверждение** → обратный отсчёт → «Исполнить» с токеном → только тогда
   команда идёт в оборудование.

Блокировки (сервер их проверяет ВСЕГДА, даже если запрос подделан):
- при активной аварии (кроме потери 110 кВ — там переброс и есть лечение) — запрещено;
- нельзя включить СВ, когда оба ввода работают (параллельная работа — опасна:
  у двух трансформаторов не бывает идеально одинакового напряжения, и между
  ними потечёт «уравнительный» ток);
- нельзя включать СВ при двух обесточенных секциях (включать нечего).

Кнопки выбираются так, чтобы случайный клик не сработал; через 10 секунд
без подтверждения выбор сбрасывается сам.

## 7. Журналы, аналитика и остальные экраны

### Журналы (ISA-18.2)

Каждое событие — запись с временем, объектом, классом (авария / ненормальный
режим / состояние / действие оператора) и приоритетом (critical/high/low/info).
ISA-18.2 — международный стандарт на журналы тревог: как правильно их
классифицировать и не «заспамить» оператора.

**Квитирование**: оператор нажимает «Подтвердить» — «я видел, разбираюсь».
Мигание прекращается, но запись остаётся красной, пока авария не уйдёт.
Так видно: авария ЕСТЬ (красная) и о ней ЗНАЮТ (не мигает).

### Аналитика (MES)

- **Период**: 5 минут... 7 дней. За сутки система сама усредняет данные
  (86 400 точек в график не влезут), поэтому сутки показываются «по 5 минут
  на точку», неделя — «по 30 минут».
- **КПЭ-сводка**: доступность % (сколько времени оборудование было в работе),
  число событий, критических аварий.
- **Метки аварий на графике**: вертикальные пунктиры в момент событий — видно
  «вот авария — и вот как просел параметр».
- **Карта Шухарта**: статистический инструмент. Процесс «в контроле», пока
  точки лежат внутри CL ± 3σ (среднее ± 3 стандартных отклонения). Выход
  за границу = процесс ведёт себя НЕ как обычно → сигнал искать причину.
- **CUSUM** — кумулятивные суммы: улавливает медленное «уползание» параметра,
  которого Шухарт не заметит (каждое значение в норме, а тренд плохой).
- **Гистограмма**: распределение значений — мода (самое частое), медиана,
  разброс.
- **Экспорт CSV/Excel**: отчёт для инженера.

### Пульт симулятора и админка

- **Пульт** (только admin): дерево объектов + шаблоны аварий + длительность.
  Это наш «стенд»: вместо реального железа создаём аварии кнопкой.
- **Админка** (только admin): пользователи, роли, **аудит входов и действий**.

### Роли

- **viewer** — только смотреть (меню «Админка» и «Пульт» скрыты, ТУ нет);
- **dispatcher** — + квитирование и телеуправление;
- **admin** — + управление пользователями и пультом.

Проверка прав на бэкенде: даже «поэлектронно» подделанный запрос вернёт 403.

### Шаг 1. Мнемосхема — главный экран (2 мин)
Открывается сразу полная схема во всю ширину. Дай 10 секунд просто посмотреть:

- Покажи клик по узлу → карточка; кнопку «☰ Объекты» → дерево; легенду цветов.

### Шаг 2. ⭐ Потеря ввода 110 кВ → переброс через СВ (4 мин)
1. ПКМ по «Ввод 110 кВ №1» → «Создать аварию» → «Потеря ввода 110 кВ», 25 с.
2. Прокомментируй происходящее: *«Ввод №1 обесточился, защита зафиксировала
   потерю, система сразу показывает оператору ЧТО случилось и ЧТО делать»*
   — покажи баннер и подсказку.
3. ТУ: клик по Секционному QF → «Включить» → отсчёт → «Исполнить».
4. Итог: СВ зелёный, Секция I подписана «через СВ», ток вернулся.
   *«Аварийное восстановление питания за 10 секунд вместо звонков и выезда».*

### Шаг 3. Журналы (1–2 мин)
Покажи critical-запись об аварии из шага 2, квитирование, осциллограмму КЗ
(если есть в списке).

### Шаг 4. Аналитика (3 мин)
Период «Сутки»: КПЭ (доступность ~99.9%, счётчики событий), график с
вертикальными метками аварий («вот она, наша авария — и виден провал мощности»),
сравнение вводов, Шухарт с числами на порогах. Скачай Excel-отчёт — покажи файл.

### Шаг 5. Пульт + админка (2 мин)
Пульт: «вот стенд, на котором мы создаём аварии». Админка: пользователи, роли,
аудит входов.

## 8. Ответы на вопросы директора

| Вопрос | Ответ |
|---|---|
| «Это работает с настоящим оборудованием?» | Протокол настоящий — Modbus TCP, понимается 90% промышленного железа. Симулятор закрыт «адаптером»: для реальной ПС меняется только конфигурация подключения. |
| «Почему нельзя было сразу к настоящей подстанции?» | Демонстрация на живом оборудовании опасна и требует согласований; симулятор воспроизводит те же протоколы и сценарии аварий безопасно. |
| «Что делать оператору при аварии ночью?» | Система сама говорит человеческим языком: «Потеря ввода 110 кВ → включите секционный QF». Мигает только то, что требует реакции. |
| «Почему PostgreSQL, а не что-то попроще?» | Одновременный доступ многих операторов + миллионы записей + отказоустойчивость. Лёгкая SQLite используется в тестах — лучшие практики обоих миров. |
| «Сколько данных держит?» | В прототипе уже ~700 тыс. измерений; PostgreSQL рассчитан на миллиарды; для сверхбольших объёмов план — TimescaleDB. |
| «А если база упадёт?» | PostgreSQL переживает сбой питания без потери данных (WAL). Плюс резервные копии — в системе есть модуль бэкапов. |
| «Кто что может?» | Роли: viewer смотрит; dispatcher подтверждает и управляет; admin управляет пользователями. Все действия — в аудите. |
| «Насколько безопасно?» | Пароли — хэш PBKDF2 с солью, доступ — JWT, права — на сервере на каждый запрос. Проводили пентест: SQL-инъекции, подделка токенов, аномальные параметры — отсекаются. |
| «Сколько до промышленной версии?» | Архитектура и документация готовы к масштабированию: реальное оборудование (смена адаптера), TimescaleDB, уведомления, резервирование сервера. |

## 9. Если что-то пойдёт не так

- **Страница пустая/старая** → Ctrl+Shift+R.
- **Сервер не отвечает** → перезапусти командой из шапки документа.
- **ТУ выдало «запрещено»** → это блокировка, НЕ баг: покажи как фичу
  («система не позволила опасную операцию»), затем устрани причину и повтори.
- **График пустой** → выбери другой период или проверь, что симулятор работает.
- Совсем всё сломалось → демо на истории: сотни тысяч точек и журналы за дни
  работают без «живого» железа.

## 10. Технические цифры (если спросят «а внутри?»)

- Backend: **Python + FastAPI**, PostgreSQL 16 + SQLAlchemy (async), pymodbus.
- Frontend: **React + TypeScript + ECharts**, сборка Vite.
- Тесты: **59 автотестов** (pytest): API, авторизация, ТУ и блокировки,
  аналитика, симулятор, резервные копии.
- Симулятор: 2 устройства Modbus TCP, 7 сценариев аварий.
- Документация: спецификация с журналом разработки (§16), руководство
  пользователя, этот сценарий демо.
